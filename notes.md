# Assumptions and design notes

## Evidence and analysis

Ten professional profiles were captured from rendered pages accessible in ordinary Chrome on
7 November 2026. The sample includes nine current Hugging Face employees and one related
Pollen Robotics professional; employer filtering requires explicit current employment.
Only observed fields are extracted. Every required section has entries in these snapshots,
but detail pages, visibility settings and lazy loading prevent a completeness guarantee.
Unknown values remain `null`; unavailable lists are distinguished from confirmed emptiness.
Capture time and source hashes provide provenance, not proof of source freshness.

The graph-analysis option is implemented: normalized skill Jaccard affinity, centrality and
communities, plus a separate directed observed-activity graph. Neither layer proves a LinkedIn
connection, reporting line or actual collaboration. Missing skills do not produce guessed
edges. Captured text may be incomplete, and relative activity dates are not exact timestamps.
All outputs, including the offline HTML explorer, are generated by the same analysis pipeline.
Its JSON payload escapes HTML delimiters; data is rendered as text and loads no remote assets.

## Online HTTP, headers and rate limiting

The guest collector uses `requests.Session`, a descriptive `User-Agent`, HTML `Accept` and
English `Accept-Language` headers. It validates HTTPS hosts and profile identities, verifies
TLS, checks `robots.txt`, bounds redirects to three, and sets 10-second connect/25-second read
timeouts. Responses are limited to 5 MiB; a 60-second streaming deadline is checked between
chunks, not enforced as a strict process deadline. Cookies are cleared after each response.

Requests are sequential with at least five seconds between starts, increased for published
crawl-delay/request-rate rules. HTTP 401/403/429/999 or login/challenge pages stop the batch;
`Retry-After` is retained in the receipt. There are no automatic retries in this implementation.
A production scheduler could retry transient timeouts/5xx with bounded exponential backoff
and jitter, honoring `Retry-After` and a shared host circuit breaker. Access denial is not a
retry or evasion opportunity. Browser collection exports visible DOM without credentials.

## Processing with Redis or Kafka

This is a proposed scaling design, not an installed runtime dependency. A producer queues
canonical URLs, capture policy/version and idempotency keys. Host-partitioned workers share
a persisted token bucket, sanitize successful snapshots and store them by content hash.
They publish object references to an extraction stream/topic. Extraction workers write
versioned normalized records and acknowledge only after durable storage. Unique keys make
at-least-once delivery idempotent. Delayed retry queues handle transient failures; malformed
or exhausted jobs go to a dead-letter queue, while access denials pause the source.

## Storage and large-scale analysis

This submission uses portable UTF-8 JSON and sanitized HTML. At scale, PostgreSQL would store
canonical people, versioned sections, activity and provenance with indexes on profile,
organization and skill IDs. Restricted object storage would hold sanitized snapshots with
retention/deletion policies; passwords and session tokens would never enter records or queues.
Parquet snapshots would support batch processing. The current O(n²) skill comparison and exact
betweenness suit a small cohort. An inverted skill index or MinHash/LSH could propose pairs
for exact verification; sampled centrality and partitioned clustering must be labeled
approximate. No Redis, Kafka or Neo4j service is required to run the delivered project.
