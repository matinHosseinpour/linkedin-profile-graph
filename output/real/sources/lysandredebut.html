    We’ve been hard at work trying to make models work with harnesses better. The best thing Younes B. found: “harness adapters”. Small LoRAs trained with RL inside the actual agent harness they’ll be used with.

    Same base model. Different adapter for pi, opencode, hermes, etc. Why?

    Simply because the same model behaves very differently depending on the tools, prompts and control flow around it. Instead of asking one set of weights to be optimal everywhere, we can specialize a tiny part of the model for each environment.

    Early results are pretty encouraging: on held-out tasks, the adapters make fewer tool calls than the base model while keeping or improving accuracy.

    And because they’re LoRAs, the operational side is surprisingly cheap too.

    For one LFM2.5-24B-A2B experiment, we evaluated 9 checkpoints / 1,350 agent sessions on a single H200 in under an hour. The total: ~$5!

    Merging and serving every checkpoint separately would have cost around $90.

    There’s another important piece: RL agents will eventually try to hack the reward.

    So every tool call goes through `safeagents`, a deterministic rule-based guard that blocks things like editing tests, tampering with rewards or bypassing the sandbox before they execute.

    And the whole loop can start from real usage:

    your coding sessions -> verifiable environments -> RL -> a better adapter for your agent.

    The model doesn’t have to change completely.

    Sometimes it just needs to get better at the harness it actually lives in.

        Lysandre Debut's experiments with individual neurons in Qwen got us curious.

        We started exploring what happens when you keep the input the same and adjust one neuron's activity while the model responds.

        Our test became a story about a shopkeeper finding an unfamiliar key. Depending on which neuron we adjusted, the story acquired dogs, turned into poetry, became a tale about electrical charges, or switched to Chinese.

        The interesting part was finding the strengths where those changes became clear. Some effects emerged gradually. Others appeared quite suddenly. Push further, and a coherent story could start falling apart.

        We've put our clearest examples into a small interactive experiment. Choose a neuron, move the slider, and compare the responses. It uses Qwen3.5-4B, with the prompt and model weights held fixed (except for the single tweaked neuron) across the experiments.

        Credit to Lysandre for the inspiration, Benjamin Bossan for his activation-steering work in PEFT, and Lyra's Neuron Explorer. We've enjoyed building on that work and making the results easier to explore. https://lnkd.in/gnQW8yiu

        LeRobot v0.7.0 is out, and this is a very big one 🦾

        You can now talk/steer a robot while it’s running; change its task:

        `/subtask pick up the red cube`

        Ask what it sees:

        `/vqa how many cubes are left?`

        Or give it a higher-level goal:

        `/autosteer clear the table`

        and let the policy or an external VLM planner figure out the subtasks!

        And this just scratches the surface of v0.7.0! Other banger features include 👇

        Training directly on huge datasets from the Hub, Storage Buckets or         LanceDB without downloading them first; particularly relevant when the Hub is already approaching !!300 TB of open Physical AI data!!

        The training stack has also been rebuilt for 5-20B parameter world action models: FSDP2, HSDP, distributed checkpoints, FP16, EMA and more.

        The model zoo keeps growing:

        - 4 new world action models, including Cosmos 3 and FLUX 3 Action
        - 4 new VLAs
        - remote inference, so the robot can stay lightweight while the policy runs on a GPU server
        - a common simulation stack that works much more like real hardware

        LeRobot is becoming less about individual robot policies and more about having one open stack from TBs of demonstrations, all the way to a robot you can interact with in real time!

            A small, on-device TTS models is competing with models up to 100× their size, and taking first place on specific benchmarks!

            Gradium's new Phonon model offers a concrete example.

            On the Open TTS Leaderboard, Gradium reports:

            - First place on intelligibility in German and Spanish.
            - Top-three intelligibility in every language it evaluated.
            - Leading CPU streaming results on time-to-first-audio.

            These results also show why it’s useful to compare TTS models on more than a single overall ranking. For the Open TTS Leaderboard, Eric Bezzam separates several dimensions:

            - Intelligibility, measured through word/character error rates.
            - Generation throughput and time-to-first-audio.
            - Predicted naturalness scores.
            - Speaker similarity for voice cloning.

            Leading on intelligibility in a particular language is a specific result, and so is leading on CPU response latency; but neither establishes that a model is best across every use case.

            For on-device applications, Phonon’s combination of size, intelligibility, and CPU latency seems really relevant. For other (heavier?) workloads, language coverage, throughput, voice similarity, or delivery may be more important.

            Your coding agent has your terminal, and your terminal has your credentials.

            But should your coding agent have access to your credentials; we don't think so, nor do we think they should upload anything to clouds without you asking. That's why             Younes B. and Nathan HABIB built safeagents.

            It’s an open-source proxy that checks an AI agent’s proposed tool calls before they execute, and blocks the ones it identifies as dangerous.

            Say you ask your agent to fix a bug, and it proposes a command to upload your ~/.netrc to a random server: from a bugfix, your credentials leak.

            Or you ask an agent to solve a coding benchmark: it finds the hidden answers, edits the verifier, patches the tests: the score goes up, yet the code is broken.

            These are the kinds of actions safeagents catches straightaway. It sits between your harness (whatever it is!) and the model API. It inspects tool calls before your harness even receives them.

            Known suspicious patterns go through rule-based checks powered by atif-scan; calls that need more judgment can go to an optional decision model.

            But which decision model can you trust to make that call?

            You're in luck, we benchmarked models on that task: catching reward hacking, sandbox escape, harness introspection, and credential misuse.

            The challenge is catching dangerous calls without blocking legitimate work, and doing it fast enough to check commands throughout an agent run. The benchmark lets you compare models, safeagents lets you plug them in.

              Agents are often difficult to predict and can produce dangerous tool calls or attempt to perform reward hacking. Potentially affecting tons of users without even noticing anything.

              Before an agent's command runs, someone should check it. We're releasing safeagents to do exactly that. Every tool call goes through it first: an upload to a bucket nobody mentioned, a request to the cloud metadata endpoint, curl --noproxy sending ~/.netrc to a paste site all get stopped before execution.

              Also handy for RL and evals: safeagents blocks a model writing its own reward.txt, editing the verifier's /tests or patching pytest to pass, before any of it runs.

              Introducing `safeagents` - a fast, free and lightweight proxy that keeps any LLM's tool calls within the task you gave it, pluggable in any coding harness. Purely written in python and based on               https://lnkd.in/d3zfuTJ8.
